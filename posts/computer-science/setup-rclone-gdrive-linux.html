How to Set Up Rclone with Google Drive: Ubuntu, Fedora & Arch Linux

DevOps
Cloud
Storage

Linux
A complete Linux-native guide to installing rclone, authenticating Google Drive, and mounting it as a persistent local filesystem.
Author

Igor Kan

Published

September 10, 2026

Rclone is an open-source command-line tool often described as “rsync for cloud storage”. It allows you to manage, sync, backup, and mount over 70 cloud storage providers—including Google Drive, Google Photos, Dropbox, S3, and OneDrive—directly on your system.

Whether you need to sync files to Google Drive, back up local directories, or seamlessly mount your Drive as a local folder, this guide covers everything from initial setup to native Linux installation and performance tuning.

1. Native Linux Installation

🐧 Ubuntu / Debian

Install rclone via the apt package manager:

sudo apt update && sudo apt install rclone

🐉 Arch Linux

Install rclone via pacman:

sudo pacman -S rclone

🎩 Fedora

Install rclone via dnf:

sudo dnf install rclone

Verify the installation:

rclone version

2. Configuring Google Drive (rclone config)

To link your Google Drive account, run the interactive configuration wizard:

rclone config
  1. New Remote: Press n.
  2. Name: Type a name like gdrive.
  3. Storage Type: Type drive.
  4. Client ID & Client Secret: Press Enter to use defaults.
  5. Scope: Choose 1 (drive - full access).
  6. Service Account File: Press Enter.
  7. Advanced Config: Press n.
  8. Auto Config:
    • Desktop: Press y to authenticate via browser.
    • Headless Server (SSH): Press n and follow instructions to authorize on another machine.
  9. Shared Drive: Press n (unless using a team drive).
  10. Confirm & Keep: Press y, then q to quit.

Test your connection:

rclone lsd gdrive:

3. Mounting Google Drive as a Local Directory

One of rclone’s most powerful features is mounting cloud storage into your local directory tree.

🐧 Linux Mount (Ubuntu, Fedora, Arch)

Create a mount point and start the mount process in the background using FUSE:

mkdir -p ~/gdrive
rclone mount gdrive: ~/gdrive --vfs-cache-mode full &

Note: The --vfs-cache-mode full flag caches reads/writes locally, allowing seamless access by applications like video players and text editors.

To unmount on Linux:

fusermount -u ~/gdrive

4. Linux: Automating Mount on Boot with Systemd

To automatically mount Google Drive in the background (even before interactive login), configure a systemd user service.

  1. Create the service file: ~/.config/systemd/user/rclone-gdrive.service:

    [Unit]
Description=Rclone Google Drive Mount
After=network-online.target
Wants=network-online.target

[Service]
Type=notify
ExecStart=/usr/bin/rclone mount gdrive: %h/gdrive \
  --config %h/.config/rclone/rclone.conf \
  --vfs-cache-mode full \
  --vfs-cache-max-size 10G \
  --umask 022
ExecStop=/bin/fusermount -u %h/gdrive
Restart=on-failure
RestartSec=10

[Install]
WantedBy=default.target

  2. Enable and start the service:

    systemctl --user daemon-reload
systemctl --user enable --now rclone-gdrive.service

  3. Enable Boot Lingering: This ensures the mount initializes at system boot, not just when you log in.

    loginctl enable-linger $USER

5. Understanding the Technologies Behind the Mount

When you mount Google Drive using rclone, you are essentially running a cloud daemon that bridges local operating systems with remote cloud architecture. This eliminates the need for resource-heavy dual sync clients (e.g., running the official Google Drive app for work and the Dropbox app for personal files simultaneously, which wastes RAM and CPU) .

Here is a breakdown of the underlying technologies and concepts:

1. Daemons and HTTPS REST / Changes API

Unlike a standard sync app that blindly downloads everything, Rclone acts as a background daemon (a silent process running continuously without a user interface). It translates your local file requests into HTTPS REST calls to the cloud provider’s API. * Example: When you create document.txt locally, Rclone issues a POST /upload/drive/v3/files request to Google’s servers. * To keep your local folder updated when someone else adds a file on the web, Rclone polls the provider’s Changes API, efficiently receiving a stream of delta updates instead of rescanning your entire 1TB cloud structure.

2. Rclone with FUSE3 and its Mount Point

On Linux, Rclone uses FUSE3 (Filesystem in Userspace) to attach the remote cloud to a local empty directory called a mount point (e.g., ~/gdrive). * Example: When you open a PDF in ~/gdrive/report.pdf, your PDF viewer thinks it’s a local file. The Linux kernel intercepts this read request, passes it to FUSE3, and FUSE3 hands it to the Rclone daemon, which seamlessly streams the PDF bytes from Google Drive.

3. Virtual Filesystem (VFS) and Virtual Mounts

Google Drive does not have a true hierarchical “filesystem” (it uses raw database IDs for files, which is why you can have two files with the same name in the same Google Drive folder). Rclone creates a Virtual Filesystem (VFS) layer to translate these database IDs into a standard folder tree structure (/folder/subfolder/file.txt). The mount is “virtual” because the folder structure exists in RAM and is projected onto the OS, rather than being written to the physical hard drive.

4. VFS Cache Mode, Sparse-File Caching, and NVMe

When you use --vfs-cache-mode full, Rclone uses VFS local sparse-file caching. * Example: If you open a 50GB 4K video from your mount, Rclone does not download 50GB before playing. It creates a “sparse” (mostly empty) placeholder file on your local disk. As your media player requests specific chunks of the video, Rclone downloads only those blocks and caches them. If your local disk is a fast NVMe SSD, this caching process is so rapid that skipping around a massive cloud video feels completely indistinguishable from playing a local file.

5. POSIX Permission Virtualization

Cloud providers don’t understand Linux ownership (UID/GID) or file permissions (like chmod 755). Rclone virtualizes these POSIX permissions locally. * Example: Using flags like --umask 022, Rclone pretends that all files on Google Drive have standard Linux read/execute permissions, preventing your local Linux applications from crashing with “Permission Denied” errors when trying to read the cloud files.

6. Systemd User Services

Instead of running Rclone manually in an open terminal, we use systemd user services (as shown in Section 4) to manage it. This turns the mount command into a resilient background service that automatically starts when you boot the computer, automatically restarts if the network drops, and cleanly unmounts when you shut down.

7. Systemd Timers and Automated Background Sync Scripts

Instead of relying on fragile cron jobs, you can use systemd timers to orchestrate your cloud architecture. Systemd timers can trigger automated bash scripts to run periodically in the background. A robust architecture separates the live FUSE mount (for daily interactive access) from scheduled background syncing (for data safety). * Example of a Sync Pipeline: Systemd Timer (2:00 AM) ──> Backup Script (rclone sync local to cloud) ──> Prune Script (rclone delete files older than 30 days) ──> Maintenance Script (rclone dedupe to fix duplicate filenames)

8. Concurrency Control: Read/Write Locks and Asynchronous Updates

  • Read/Write Locks: When you edit a file, multiple processes might try to access it simultaneously. Rclone’s VFS layer enforces POSIX-compliant read/write locks, ensuring that if a text editor is saving a file, a background backup process cannot read it until the save completes, preventing data corruption.
  • Asynchronous Updates: When you hit “Save”, the write is committed instantly to your local sparse-file cache. Rclone then performs an asynchronous update, uploading the file to Google Drive in the background. Your application regains control instantly without freezing to wait for the network.

9. Data Integrity & Verification Scripts

  • Concept: Network drops or API timeouts can occasionally cause silent data corruption during massive transfers.
  • Verification Scripts: You can automate integrity checks using rclone check in your bash scripts. Rclone fetches cryptographic hashes (like MD5) from the cloud API and compares them against your local files. This provides mathematical verification that your remote backups are identical to your local copies without actually re-downloading the data.

10. Filesystem Interoperability and Methods

  • Concept: Interoperability ensures that files created in one environment (e.g., Linux GUI apps like LibreOffice) can be seamlessly utilized in another (e.g., Linux command-line).
  • Methods: The architecture achieves this via abstraction layers. The Linux kernel’s Virtual File Switch (VFS) and FUSE allow standard GUI applications to access the cloud drive exactly as they would a local ext4 partition. Since Rclone treats file contents opaquely, you can use grep to parse a log file stored on Google Drive while a graphical application is simultaneously appending new lines to it, with the filesystem maintaining complete interoperability.

6. Performance Tuning for Bulk Uploads

If you need to backup hundreds of gigabytes (e.g., massive media or dataset folders), standard copy commands can be slow. Use these optimized flags to maximize bandwidth and minimize API overhead:

rclone copy ~/Downloads gdrive:Downloads \
  --fast-list \
  --transfers=8 \
  --checkers=16 \
  --stats 10s
  • --fast-list: Uses recursive API directory listings, significantly reducing HTTP request overhead.
  • --transfers=8: Uploads 8 files in parallel.
  • --checkers=16: Uses 16 parallel threads to compare file hashes.

7. Re-connecting an Expired Remote

Google Drive tokens expire periodically. If you receive an invalid_grant authentication error, reconnect quickly without deleting your configuration:

rclone config reconnect gdrive:

Follow the prompt to re-authenticate via your web browser.
