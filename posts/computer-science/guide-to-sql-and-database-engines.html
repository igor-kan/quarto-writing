1. Introduction: The Declarative Power of SQL

Structured Query Language (SQL) is the universal lingua franca of data engineering, software architecture, and analytical systems. Unlike imperative languages (such as Python, C++, or Rust) where the programmer dictates how a machine iterates through memory, SQL is strictly declarative: you specify what mathematical relation you want to produce, and the database engine’s query planner compiles, optimizes, and executes an access path.

However, writing performant, bug-free, and sophisticated SQL requires understanding how database engines actually interpret code. When developers transition from basic SELECT ... FROM ... WHERE queries to production data pipelines and algorithmic challenges (like LeetCode SQL), they run directly into engine discrepancies, execution order traps, and complex relational constructs.

This comprehensive guide serves as an all-in-one, multi-dialect masterclass comparing the five dominant relational database engines:

  • PostgreSQL (pgsql) — The open-source extensible standard of modern backend engineering.
  • MySQL (mysql) — The ubiquitous web workhorse powering massive read-heavy systems.
  • Microsoft SQL Server (msserver / T-SQL) — The enterprise standard with deep tooling.
  • Oracle Database (oracle / PL-SQL) — The mission-critical financial and transaction powerhouse.
  • SQLite (sqlite) — The serverless, zero-configuration embedded engine running on billions of devices.

2. The True Order of SQL Execution (Why WHERE Fails on Window Functions)

One of the most pervasive misconceptions among intermediate developers is reading SQL in the order it is written. In written syntax, SELECT appears first:

SELECT department_id, AVG(salary) AS avg_sal  -- Line 1
FROM employees                                 -- Line 2
WHERE salary > 50000                           -- Line 3
GROUP BY department_id                         -- Line 4
HAVING AVG(salary) > 80000                     -- Line 5
ORDER BY avg_sal DESC                          -- Line 6
LIMIT 10;                                      -- Line 7

However, the database engine executes this query in a completely different, strict sequential order:

The Two Critical Pitfalls Explained:

  1. Why WHERE avg_sal > 80000 Errors:
    • In Step 2 (WHERE), the SELECT clause (Step 6) has not executed yet. The alias avg_sal does not exist in memory!
    • Furthermore, AVG(salary) is an aggregate, which can only be computed after rows are grouped in Step 3. Filtering aggregates must happen in HAVING (Step 4).
  2. Why WHERE DENSE_RANK() OVER (...) <= 2 is Illegal:
    • Window functions execute in Step 5 (WINDOW), after WHERE has already executed in Step 2.
    • A database cannot filter rows using a window function in the same query block because the window function requires the post-WHERE dataset to define its partitions!
    • The Universal Solution: Wrap the window function inside a Common Table Expression (CTE) or a derived subquery, allowing the outer query’s WHERE clause to filter the computed rank.

3. Window Functions Masterclass: Ranking, Values, and Frames

Window functions perform calculations across a set of table rows that are related to the current row, without collapsing the individual rows into a single summary line (unlike GROUP BY).

\[\text{\bf Syntax: } \text{FUNCTION}(\dots) \text{ OVER } \Big( [\text{PARTITION BY } c_1, c_2, \dots] \quad [\text{ORDER BY } s_1, s_2, \dots] \quad [\text{FRAME\_CLAUSE}] \Big)\]

1. The Ranking Functions Compared: ROW_NUMBER vs RANK vs DENSE_RANK vs NTILE

Suppose four students achieve test scores: [100, 95, 95, 80]. Here is how each function handles identical values (ties):

Student Score ROW_NUMBER() RANK() DENSE_RANK() NTILE(2) Notes on Behavior
Alice 100 1 1 1 1 Highest score.
Bob 95 2 2 2 1 Tied for 2nd place.
Charlie 95 3 2 2 2 Tied for 2nd place. ROW_NUMBER breaks tie arbitrarily.
David 80 4 4 3 2 RANK leaves a gap (skips 3). DENSE_RANK has no gaps!
  • ROW_NUMBER(): Assigns a strictly unique, contiguous integer to every row. Essential for deterministic pagination and deduplication.
  • RANK(): Assigns equal integers to ties, but leaves gaps in subsequent rankings (1, 2, 2, 4…). Matches Olympic medal standing.
  • DENSE_RANK(): Assigns equal integers to ties without gaps (1, 2, 2, 3…). Essential for “Find the Top \(N\) highest unique salaries.”
  • NTILE(n): Divides rows into \(n\) roughly equal percentile buckets (quartiles, deciles).

2. Positional & Value Functions: LAG, LEAD, FIRST_VALUE, LAST_VALUE

Value functions inspect adjacent or boundary rows relative to the current row:

SELECT 
    emp_id, 
    department_id, 
    hire_date, 
    salary,
    -- Inspect previous employee's salary in the department
    LAG(salary, 1, 0) OVER (
        PARTITION BY department_id 
        ORDER BY hire_date ASC
    ) AS prev_salary,
    -- Inspect next employee's salary in the department
    LEAD(salary, 1, 0) OVER (
        PARTITION BY department_id 
        ORDER BY hire_date ASC
    ) AS next_salary,
    -- Salary of the very first hire in the department
    FIRST_VALUE(salary) OVER (
        PARTITION BY department_id 
        ORDER BY hire_date ASC 
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS first_hire_salary
FROM employees;
WarningThe Infamous LAST_VALUE() Default Frame Trap

When an ORDER BY is provided inside an OVER () clause, ANSI SQL mandates a default window frame: \[\text{RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW}\] Because the frame terminates at the CURRENT ROW, calling LAST_VALUE(col) OVER (ORDER BY col) will return the current row’s value rather than the last value of the entire partition! The Fix: Explicitly expand the window frame to the end of the partition:

LAST_VALUE(salary) OVER (
    PARTITION BY department_id 
    ORDER BY hire_date ASC
    ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
) AS true_last_hire_salary

4. Common Table Expressions (CTEs) & Recursive Hierarchies

A Common Table Expression (CTE) defines a temporary, named result set that exists solely within the execution scope of a single SQL statement.

1. Non-Recursive CTE for Filtering Window Functions

As established in Section 2, window functions cannot be filtered directly in WHERE. The standard, clean architectural pattern is a CTE:

WITH RankedSalaries AS (
    SELECT 
        department_id,
        employee_id,
        salary,
        DENSE_RANK() OVER (
            PARTITION BY department_id 
            ORDER BY salary DESC
        ) AS salary_rank
    FROM employees
)
SELECT department_id, employee_id, salary
FROM RankedSalaries
WHERE salary_rank <= 3;  -- Top 3 distinct earners per department

2. Recursive CTEs for Hierarchical and Graph Traversal

Recursive CTEs solve self-referential tree problems (e.g., corporate reporting structures, folder directories, bill of materials).

A recursive CTE consists of: 1. The Anchor Member: The base query that initializes the recursion (e.g., finding the CEO where manager_id IS NULL). 2. UNION ALL 3. The Recursive Member: The query referencing the CTE itself, joining the child rows to parent rows. 4. Termination Condition: Implicitly halts when the recursive join yields an empty set.

Universal Recursive CTE (PostgreSQL, MySQL 8.0+, SQLite):

WITH RECURSIVE OrgTree AS (
    -- Anchor Member: Root CEO
    SELECT 
        employee_id, 
        manager_id, 
        employee_name, 
        1 AS depth, 
        CAST(employee_name AS VARCHAR(1000)) AS hierarchy_path
    FROM corporate_staff
    WHERE manager_id IS NULL

    UNION ALL

    -- Recursive Member: Subordinates
    SELECT 
        c.employee_id, 
        c.manager_id, 
        c.employee_name, 
        p.depth + 1, 
        CAST(CONCAT(p.hierarchy_path, ' -> ', c.employee_name) AS VARCHAR(1000))
    FROM corporate_staff c
    INNER JOIN OrgTree p ON c.manager_id = p.employee_id
)
SELECT depth, hierarchy_path 
FROM OrgTree 
ORDER BY hierarchy_path;

Engine Dialect Differences for Recursive CTEs:

  • SQL Server (T-SQL): Omits the RECURSIVE keyword (WITH OrgTree AS (...)).
  • Oracle: Supports both standard ANSI WITH recursive CTEs (11gR2+) and proprietary START WITH manager_id IS NULL CONNECT BY PRIOR employee_id = manager_id.

5. Complex Joins, Multi-Column Keys & Self-Referential Rules

1. Multi-Column Joins (Composite Keys)

In enterprise databases and data warehouses, tables are frequently related by compound primary keys (e.g., multi-tenant systems where every table includes a tenant_id and store_id):

SELECT 
    f.transaction_id,
    f.amount,
    d.department_name
FROM fact_sales f
INNER JOIN dim_department d 
    ON f.tenant_id     = d.tenant_id
   AND f.store_id      = d.store_id
   AND f.department_id = d.department_id
WHERE f.fiscal_year = 2026;

2. Non-Equi Joins (Interval & Range Matching)

Joins do not require equality (=). Non-equi joins match records across temporal ranges or thresholds:

-- Find employee performance ratings based on salary bands
SELECT 
    e.employee_name,
    e.salary,
    b.grade_level
FROM employees e
INNER JOIN salary_bands b 
    ON e.salary >= b.min_salary 
   AND e.salary <  b.max_salary;

3. Self-Joins & Self-Referential Matching

A self-join joins a table to itself under distinct aliases. Common use cases include:

A. Finding Managers of Employees:

SELECT 
    emp.employee_name AS subordinate,
    mgr.employee_name AS manager
FROM employees emp
LEFT JOIN employees mgr ON emp.manager_id = mgr.employee_id;

B. Overlapping Date Intervals (Collision Detection):

-- Detect overlapping room reservations
SELECT 
    r1.reservation_id AS res1,
    r2.reservation_id AS res2,
    r1.room_id
FROM reservations r1
INNER JOIN reservations r2 
    ON r1.room_id = r2.room_id
   AND r1.reservation_id < r2.reservation_id  -- Avoid mirror pairs and self-match
   AND r1.start_time < r2.end_time 
   AND r1.end_time > r2.start_time;

6. Array & Collection Unnesting Across All 5 Engines

Modern schemas frequently store arrays, repeated records, or JSON documents. Unnesting (or “exploding”) expands an array of \(N\) elements into \(N\) separate rows.

Because array implementations vary dramatically across engines, here is the concrete syntax for each:

1. PostgreSQL (Native Arrays)

-- Input: Table with an integer array column: tags INT[] = '{101, 102, 103}'
SELECT 
    item_id, 
    unnested_tag.tag_id,
    unnested_tag.ordinality
FROM items,
UNNEST(items.tags) WITH ORDINALITY AS unnested_tag(tag_id, ordinality);

2. MySQL (JSON Arrays via JSON_TABLE)

-- Input: Table with a JSON array column: tags_json = '[101, 102, 103]'
SELECT 
    i.item_id, 
    jt.tag_id
FROM items i,
JSON_TABLE(
    i.tags_json, 
    '$[*]' COLUMNS (tag_id INT PATH '$')
) AS jt;

3. Microsoft SQL Server (STRING_SPLIT & OPENJSON)

-- A. Unnesting comma-delimited strings:
SELECT item_id, TRIM(value) AS tag_id
FROM items
CROSS APPLY STRING_SPLIT(tags_csv, ',');

-- B. Unnesting JSON arrays:
SELECT item_id, CAST(value AS INT) AS tag_id
FROM items
CROSS APPLY OPENJSON(tags_json);

4. Oracle (JSON_TABLE & Nested Tables)

-- Unnesting JSON array in Oracle 12c+:
SELECT i.item_id, jt.tag_id
FROM items i,
JSON_TABLE(
    i.tags_json, 
    '$[*]' COLUMNS (tag_id NUMBER PATH '$')
) jt;

5. SQLite (json_each)

-- SQLite supports JSON extension natively:
SELECT i.item_id, j.value AS tag_id
FROM items i,
json_each(i.tags_json) j;

7. String & Array Aggregations (The Reverse of Unnesting)

When grouping rows, developers often need to collapse multiple child strings into a single comma-separated list:

Engine Aggregation Syntax Example
PostgreSQL STRING_AGG(col, delimiter [ORDER BY ...]) STRING_AGG(name, ', ' ORDER BY name ASC)
MySQL GROUP_CONCAT([DISTINCT] col [ORDER BY ...] SEPARATOR delimiter) GROUP_CONCAT(name ORDER BY name ASC SEPARATOR ', ')
SQL Server STRING_AGG(col, delimiter) WITHIN GROUP (ORDER BY ...) STRING_AGG(name, ', ') WITHIN GROUP (ORDER BY name ASC)
Oracle LISTAGG(col, delimiter) WITHIN GROUP (ORDER BY ...) LISTAGG(name, ', ') WITHIN GROUP (ORDER BY name ASC)
SQLite GROUP_CONCAT(col [, delimiter]) GROUP_CONCAT(name, ', ')

8. Bitwise Operations & Parity Manipulation in SQL

Bitwise operators allow lightning-fast bit-level arithmetic directly inside relational queries.

Operation PostgreSQL MySQL SQL Server SQLite Oracle
Bitwise AND a & b a & b a & b a & b BITAND(a, b)
Bitwise OR a \| b a \| b a \| b a \| b a + b - BITAND(a, b)
Bitwise XOR a # b a ^ b a ^ b a ^ b Proprietary formula / UDF
Bitwise NOT ~a ~a ~a ~a -1 - a
Left Shift a << n a << n Not native (a * POWER(2,n)) a << n a * POWER(2, n)

Practical LeetCode Parity Trick: Alternating Seat Swaps

To swap odd/even IDs (\(1 \leftrightarrow 2, 3 \leftrightarrow 4\)): * For zero-indexed numbers, XOR with 1 swaps pairs: \(0 \leftrightarrow 1, 2 \leftrightarrow 3\). * For one-indexed numbers: \[\text{new\_id} = ((id - 1) \oplus 1) + 1\] In MySQL / SQL Server / SQLite: ((id - 1) ^ 1) + 1.

9. Character & ASCII Code Conversions

Converting between ASCII numerical values and their string character representations:

1. ASCII Code to Character

  • PostgreSQL / Oracle / SQLite: CHR(65) \(\longrightarrow\) 'A'
  • MySQL / SQL Server: CHAR(65) \(\longrightarrow\) 'A'

2. Character to ASCII Code

  • Universal across all 5 engines: ASCII('A') \(\longrightarrow\) 65

3. Practical Example: Generating the Alphabet \(A-Z\) in Pure SQL (PostgreSQL):

SELECT CHR(ascii_code) AS letter
FROM generate_series(65, 90) AS ascii_code;

10. Statistical Bucketing & Pure-SQL Distribution Charts

Visualizing distributions (such as LeetCode score distributions or transaction frequency histograms) can be accomplished directly inside SQL using bucketing and text repetition functions.

1. Generating Equal-Width Histogram Buckets

PostgreSQL and Oracle feature the native WIDTH_BUCKET() function:

\[\text{WIDTH\_BUCKET}(\text{value}, \text{min}, \text{max}, \text{num\_buckets})\]

For engines lacking WIDTH_BUCKET (MySQL, SQL Server, SQLite), use math floor:

-- Put scores [0, 100] into 10 buckets of width 10:
SELECT 
    FLOOR(score / 10.0) * 10 AS bucket_min,
    COUNT(*) AS frequency
FROM exam_results
GROUP BY FLOOR(score / 10.0) * 10
ORDER BY bucket_min;

2. Rendering ASCII Bar Charts in Pure SQL

By scaling counts and repeating a UTF-8 bar character (█), queries can output visual charts directly into terminal consoles:

PostgreSQL & MySQL:

WITH ScoreBins AS (
    SELECT 
        FLOOR(score / 10.0) * 10 AS bin_start,
        COUNT(*) AS student_count
    FROM exam_results
    GROUP BY FLOOR(score / 10.0) * 10
)
SELECT 
    CONCAT(bin_start, ' - ', bin_start + 9) AS score_range,
    student_count,
    REPEAT('█', CAST(student_count / 2 AS INT)) AS distribution_chart
FROM ScoreBins
ORDER BY bin_start ASC;

Output Representation:

score_range  | student_count | distribution_chart
0 - 9        | 2             | █
10 - 19      | 5             | ██
20 - 29      | 12            | ██████
30 - 39      | 24            | ████████████
40 - 49      | 18            | █████████

11. Classic LeetCode SQL Patterns (Deconstructed with Code)

Case Study 1: Triangle Judgement (LeetCode 610)

  • Problem: Given three side lengths \(x, y, z\), determine whether they can form a valid triangle.
  • Mathematical Condition: The sum of any two sides must be strictly greater than the remaining side: \[(x + y > z) \quad \land \quad (x + z > y) \quad \land \quad (y + z > x)\]
  • Universal SQL Solution:
SELECT 
    x, y, z,
    CASE 
        WHEN x + y > z AND x + z > y AND y + z > x THEN 'Yes'
        ELSE 'No'
    END AS triangle
FROM Triangle;

Case Study 2: Department Top Three Salaries (LeetCode 185)

  • Problem: A company wants to find employees who earn top 3 unique salaries in each department.
  • Why RANK() Fails: If salaries are [100k, 90k, 90k, 80k], RANK assigns [1, 2, 2, 4]. Rank 4 is skipped, missing the third tier!
  • The DENSE_RANK() Solution:
WITH RankedEmployees AS (
    SELECT 
        d.name AS Department,
        e.name AS Employee,
        e.salary AS Salary,
        DENSE_RANK() OVER (
            PARTITION BY e.departmentId 
            ORDER BY e.salary DESC
        ) AS rnk
    FROM Employee e
    INNER JOIN Department d ON e.departmentId = d.id
)
SELECT Department, Employee, Salary
FROM RankedEmployees
WHERE rnk <= 3;

Case Study 3: Consecutive Numbers (LeetCode 180)

  • Problem: Find all numbers that appear at least three times consecutively in a log table.

Method A: Modern Window Functions (LAG & LEAD)

WITH ConsecutiveScan AS (
    SELECT 
        num,
        LAG(num, 1)  OVER (ORDER BY id) AS prev_num,
        LEAD(num, 1) OVER (ORDER BY id) AS next_num
    FROM Logs
)
SELECT DISTINCT num AS ConsecutiveNums
FROM ConsecutiveScan
WHERE num = prev_num AND num = next_num;

Method B: 3-Way Self-Join (Compatible with any SQL version):

SELECT DISTINCT l1.num AS ConsecutiveNums
FROM Logs l1
INNER JOIN Logs l2 ON l1.id = l2.id - 1
INNER JOIN Logs l3 ON l1.id = l3.id - 2
WHERE l1.num = l2.num AND l2.num = l3.num;

Case Study 4: Exchange Seats (LeetCode 626)

  • Problem: Swap consecutive odd and even seats. If the last seat is odd, do not swap it.

Universal SQL Solution via CASE & Window Count:

SELECT 
    CASE 
        -- If odd and last seat, keep as is
        WHEN id % 2 = 1 AND id = (SELECT COUNT(*) FROM Seat) THEN id
        -- If odd, increment to next even seat
        WHEN id % 2 = 1 THEN id + 1
        -- If even, decrement to previous odd seat
        ELSE id - 1
    END AS id,
    student
FROM Seat
ORDER BY id ASC;
