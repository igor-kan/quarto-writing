Setting Up an Automated Rclone FUSE Google Drive Mount on Windows WSL2

A complete guide to configuring Rclone with FUSE and systemd inside WSL2, featuring VFS full caching, Windows drive letter mapping, and automated background sync.
Author

Igor Kan

Published

September 10, 2026

Integrating cloud storage into a developer workflow often comes down to a difficult choice: native desktop sync clients that consume excessive disk space, or CLI tools that require manual uploads and lack transparent filesystem access.

On Linux distributions such as Arch, the standard gold-plate architecture pairs Rclone with FUSE3 and systemd user services. This provides a real-time, on-demand virtual filesystem with local sparse-file caching (--vfs-cache-mode full), POSIX permission virtualization, and automated background sync scripts.

When transitioning to a Windows laptop with WSL2 (Windows Subsystem for Linux), you can completely replicate this Linux-native cloud architecture inside WSL2—and even map the resulting virtual mount as a native drive letter in Windows File Explorer.

Architectural Overview

Rather than running dual sync clients or clunky third-party Windows drivers (such as WinFsp), this architecture isolates the cloud daemon and automation pipelines entirely inside WSL2:

┌────────────────────────────────────────────────────────┐
│                     Google Drive                       │
└───────────────────────────▲────────────────────────────┘
                            │ HTTPS REST / Changes API
┌───────────────────────────▼────────────────────────────┐
│              WSL2 Linux Environment                    │
│                                                        │
│  systemd (user) ──> rclone mount daemon                │
│       │             ├── NVMe VFS Cache (~/.cache/rclone)
│       │             └── FUSE3 Mount Point (~/gdrive)   │
│       │                                                │
│  systemd timers ──> Backup / Prune / Maintenance       │
└───────────────────────────▲────────────────────────────┘
                            │ Plan9 (9P) Network Protocol
┌───────────────────────────▼────────────────────────────┐
│                    Windows 11 Host                     │
│                                                        │
│  Windows File Explorer ──> Network Drive (G:\)         │
│  Native Windows Apps   ──> \\wsl$\...\home\user\gdrive │
└────────────────────────────────────────────────────────┘

Key Advantages:

  1. Zero Dual-Cache Conflicts: A single daemon manages read/write locks and asynchronous uploads.
  2. Native POSIX Scripting: Your bash scripts, Python verification checks, and systemd timers run without modification.
  3. Sparse-File VFS Caching: Only downloaded or modified chunks are stored locally, capping SSD usage.
  4. Seamless Interoperability: Files modified in Windows applications (Photoshop, VS Code, Office) are instantly detected and uploaded by the WSL2 Rclone process.

Architectural Deep-Dive: Terms & Core Concepts

To understand why this architecture is far superior to standard commercial sync tools, let us break down each underlying concept, technology, and protocol:

1. Rclone and Cloud Daemons

  • Concept: While standard Rclone is a synchronous CLI tool (like rsync), running rclone mount transforms it into a long-running daemon—a background service with no graphical user interface that runs continuously.
  • How it Works: The daemon intercepts local operating system system calls (such as open(), read(), write(), close()) and translates them into cloud API actions. It maintains active worker threads to process asynchronous background uploads and downloads.
  • Example: Opening notes.txt in a local text editor makes the editor issue standard POSIX read() calls. The Rclone daemon streams only the required bytes over HTTPS, making remote files feel local.

2. Eliminating Dual Sync Clients & Clunky Windows Drivers

  • The Problem: Many users run multiple official sync clients simultaneously—such as Google Drive for Desktop alongside Dropbox or OneDrive. Each client runs its own separate background process, consumes hundreds of megabytes of RAM, runs redundant disk indexing services, and competes for filesystem locks.
  • The Driver Problem: Native Windows mounting utilities (like WinFsp or Dokan) require low-level Windows kernel filesystem filter drivers. These third-party drivers frequently break after major Windows Updates, introduce memory leaks, or trigger Blue Screens of Death (BSOD).
  • The Solution: Isolating the mount inside WSL2 completely eliminates the need for Windows kernel drivers. A single Rclone daemon handles all cloud remotes, consuming minimal RAM and zero Windows kernel attack surface.

3. Cloud Architecture & HTTPS REST / Changes API

  • Cloud Architecture: Cloud providers like Google Drive do not store files in standard filesystem blocks or inodes; they operate as object databases where each file is an opaque blob addressed by a unique alphanumeric ID string.
  • HTTPS REST API: When your application requests a file, Rclone executes HTTPS REST requests (e.g., GET https://www.googleapis.com/drive/v3/files/{fileId}?alt=media).
  • Changes API: Rather than crawling through thousands of directories every few seconds to detect changes (which quickly exhausts API rate limits), Rclone polls Google’s Changes API (drive.changes.list). This returns an incremental stream of delta changes (new files, modified timestamps, deleted IDs), updating the local directory view in near real-time with negligible network overhead.

4. FUSE3 and Mount Points

  • FUSE (Filesystem in Userspace): In traditional Unix systems, filesystems must be written as privileged kernel modules. FUSE allows unprivileged user programs to create custom filesystems. FUSE3 is the modern iteration offering enhanced multithreading and asynchronous I/O capabilities.
  • Mount Point: A standard, empty directory in your Linux tree (e.g., ~/gdrive) designated as the attachment point for the virtual filesystem.
  • Mechanism: When an application accesses ~/gdrive, the Linux Virtual File Switch (VFS) routes the request through /dev/fuse to the user-space Rclone process, which serves the file from memory, cache, or the cloud.

5. Virtual Filesystem (VFS) and Virtual Mounts

  • Concept: A virtual mount creates the illusion of a full filesystem hierarchy without allocating corresponding disk blocks on physical storage.
  • VFS Translation Layer: Because Google Drive permits multiple files with identical names in the same parent folder and organizes data by database IDs, Rclone’s VFS layer builds an in-memory directory tree that conforms to standard POSIX hierarchy rules (/path/to/filename.ext).

6. Cache Modes, Local Sparse-File Caching, and NVMe SSDs

  • Cache Modes:
    • --vfs-cache-mode off: Direct streaming; no seek support and read-only for many applications.
    • --vfs-cache-mode writes: Caches files only when modified locally.
    • --vfs-cache-mode full: The gold standard. Supports full random reads, writes, memory mapping (mmap), and append operations.
  • Local Sparse-File Caching: Under full cache mode, Rclone does not download an entire file before opening it. If you open a 20 GB video file to check the final 10 seconds, Rclone creates a sparse file on your local drive. It allocates disk blocks only for the requested 10-second segment, leaving the rest as unallocated “holes”.
  • NVMe Integration: Storing this cache (~/.cache/rclone/) on a fast NVMe SSD ensures that chunk lookups, hash verifications, and buffer flushes operate at multi-gigabyte-per-second bus speeds, making remote cloud access indistinguishable from local drive performance.

7. POSIX Permission Virtualization

  • Concept: Google Drive possesses no native awareness of Linux users, groups, or POSIX mode bits (rwxr-xr-x).
  • Virtualization: When mounting, Rclone virtualizes these permissions dynamically. Passing --umask 022 ensures files appear with standard 0644 (read/write for owner, read for others) and directories with 0755 permissions. Local Linux scripts, daemons, and SSH servers can interact with these files without triggering permission errors.

8. Automated Background Sync Scripts and Their Types

While a live FUSE mount is optimal for interactive browsing, scheduled background sync scripts provide deterministic backup guarantees. Common script patterns include: 1. One-Way Mirror (rclone sync): Modifies destination to match source precisely, adding new files and deleting removed ones. * Example: Nightly sync of ~/Documents to gdrive:Backup/Documents. 2. Incremental Snapshot Backup (--backup-dir): Moves overwritten or deleted files into a date-stamped folder, creating an immutable historic archive. * Example: rclone sync ~/Code gdrive:Code --backup-dir gdrive:Archive/$(date +%Y-%m-%d). 3. Bidirectional Synchronization (rclone bisync): Propagates changes made on either side with conflict-detection heuristics. 4. Maintenance & Deduplication (rclone dedupe): Resolves duplicate filenames that may occur on Google Drive due to concurrent web uploads.

9. Windows Drives (Drive Letters vs. Network Drives) & WSL2

  • Windows Drive Architecture: Windows traditionally identifies storage volumes by single drive letters (C:\ for the system NTFS partition, D:\ for secondary drives).
  • Local vs. Network Drives: While C:\ represents a local physical drive controlled by an internal storage controller, drive letters can also be mapped to network resources (Network Drives) defined by UNC paths (Universal Naming Convention, e.g., \\server\share).
  • WSL2 Integration: WSL2 runs inside an optimized Hyper-V utility virtual machine with its own Linux kernel. Windows File Explorer accesses the WSL2 virtual disk via the special UNC network provider \\wsl$\<DistroName>\. Mapping this path to a drive letter like G:\ lets legacy Windows applications (like Office, MATLAB, or Adobe) access your cloud files as if they were on a physical local disk.

10. The Plan9 (9P) Network Protocol

  • Origin & Architecture: Originally developed at Bell Labs as part of the Plan 9 operating system, the 9P network protocol treats all system resources, devices, and files as network-accessible file systems.
  • Role in WSL2: Microsoft chose the 9P protocol to bridge the boundary between the Windows host kernel and the WSL2 guest Linux kernel.
  • Mechanism: A 9P server runs inside the WSL2 guest, exposing the Linux VFS (including Rclone’s FUSE mount). The Windows NT kernel runs an internal 9P client that communicates with this server across Hyper-V’s lightning-fast virtual VM bus (VMBus). This allows Windows applications to read and write to the Linux-mounted Google Drive at RAM-bus speed without any physical network interface overhead.

11. Systemd User Services & Systemd Timers (Backup, Prune, Maintenance)

  • Systemd User Services (systemctl --user): Manage user-level background daemons that run independently of root. When session lingering is enabled (loginctl enable-linger), these services start automatically during boot and continue running even when no shell is open.

  • Systemd Timers: The modern, robust successor to cron. Timers provide precise scheduling, monotonic time delays, wake-on-event triggers, and integrated logging via journalctl.

  • The Automated Lifecycle Pipeline:

    ┌──────────────────────────────────────────────────────────────┐
│                   Daily Maintenance Pipeline                 │
└──────────────────────────────────────────────────────────────┘
  │
  ├── 1. Backup Timer (02:00) ──> rclone sync --backup-dir
  │      Creates date-stamped differential backup of local work
  │
  ├── 2. Prune Timer (03:00)  ──> rclone delete --min-age 30d
  │      Purges snapshots older than retention policy (e.g. 30 days)
  │
  └── 3. Maint Timer (04:00)  ──> rclone cleanup & vfs purge
         Flushes orphaned cache chunks and cleans Google Drive trash

12. Concurrency Control: Read/Write Locks and Asynchronous Updates

  • Read/Write Locks: When you edit a file, multiple processes might try to read or write to it simultaneously. Rclone’s VFS layer enforces POSIX-compliant read/write locks, ensuring that if a text editor is writing to a file, a background backup process cannot read it until the write is complete, preventing data corruption.
  • Asynchronous Updates: When you hit “Save” on a large document, the write operation is committed instantly to your local VFS cache. The Rclone daemon then performs an asynchronous update—uploading the file to Google Drive in the background. Your text editor regains control instantly without freezing to wait for the network upload to finish.

13. Data Integrity & Verification Scripts

  • Concept: Network drops or API errors can silently corrupt uploads. Verification scripts automate the checking of file integrity between local and remote endpoints without re-downloading files.
  • How it Works: Scripts leveraging rclone check or custom Python automation fetch cryptographic hashes (MD5, SHA1) directly from the Google Drive API and compare them against the local cache. If a mismatch is detected, the script can trigger a re-upload, guaranteeing mathematical data parity.

14. Cross-Platform Interoperability and Methods

  • Concept: Working simultaneously with Linux CLI tools and Windows graphical applications creates pathing and permission conflicts.
  • Interoperability Methods: The architecture handles this via translation layers. Windows paths (C:\) and WSL network paths (\wsl$) are unified through the 9P protocol. Line endings (CRLF vs LF) are preserved perfectly because Rclone treats files as binary objects. This means you can run a sed script against ~/gdrive/config.txt in Linux, and subsequently edit the exact same file in Windows Notepad via G:\config.txt without corrupting formatting.

Step 1: Enable Systemd in WSL2

Modern WSL2 includes native support for systemd, which is essential for user services (systemctl --user), timers, and lingering daemons.

  1. In your WSL terminal, open or create /etc/wsl.conf:

    sudo nano /etc/wsl.conf

  2. Add the [boot] section to enable systemd:

    [boot]
systemd=true

  3. Save the file (Ctrl+O, Enter, Ctrl+X).

  4. Open PowerShell on Windows and issue a full shutdown to apply the configuration:

    wsl --shutdown

  5. Reopen your WSL terminal. Verify that systemd is active:

    systemctl is-system-running

    (It should report running or degraded if some optional system units are skipped—both are completely fine for user services).

Step 2: Install Rclone and FUSE3

Install the required packages in your WSL distribution:

sudo apt update
sudo apt install rclone fuse3 -y

Note on dpkg locks: If you receive an error stating dpkg was interrupted, recover the package manager by running sudo dpkg --configure -a before re-running apt install.

Step 3: Configure FUSE Multi-User Permissions

Because Windows accesses WSL filesystems through a 9P network redirector under a distinct user mapping, FUSE mounts must allow other users to traverse the mount point.

  1. Open /etc/fuse.conf:

    sudo nano /etc/fuse.conf

  2. Locate the commented-out directive:

    #user_allow_other

  3. Uncomment the line by removing the #:

    user_allow_other

  4. Save and exit.

Step 4: Configure Google Drive Remote (rclone config)

To prevent API rate limits and throttling caused by shared application credentials, configure your own OAuth Client ID through the Google Cloud Console.

Creating Personal Google Cloud Credentials

  1. Visit the Google Cloud Console.
  2. Create a project named Rclone-Personal.
  3. In APIs & Services > Library, search for Google Drive API and click Enable.
  4. In APIs & Services > OAuth consent screen:
    • User Type: External
    • App Name: Rclone
    • User Support & Developer Email: Your Google email.
    • Test Users: Add your Google account email.
  5. In APIs & Services > Credentials:
    • Click Create Credentials > OAuth client ID.
    • Application Type: Desktop app.
    • Name: Rclone Desktop.
  6. Copy the generated Client ID and Client Secret.

Running the Wizard

In WSL, run:

rclone config
  1. Press n for New remote.
  2. Name: gdrive.
  3. Storage Type: drive (Google Drive).
  4. Paste your Client ID and Client Secret.
  5. Scope: Select 1 (drive - full access).
  6. When prompted to Use web browser to automatically authenticate?, choose y.
    • WSL2 will automatically forward the authentication URL to your default Windows web browser.
    • Log into your Google account and grant permissions.
  7. Confirm the remote and quit (q).

Verify connectivity:

rclone lsd gdrive:

Step 5: Construct the Rclone VFS Systemd Service

Create a dedicated mount directory in your WSL home folder:

mkdir -p ~/gdrive

Next, establish a systemd user unit that mounts the drive automatically on boot:

  1. Create the user service directory:

    mkdir -p ~/.config/systemd/user

  2. Create ~/.config/systemd/user/rclone-gdrive.service:

    nano ~/.config/systemd/user/rclone-gdrive.service

  3. Insert the production-tuned service configuration:

    [Unit]
Description=Rclone Google Drive VFS Mount
Documentation=https://rclone.org/commands/rclone_mount/
After=network-online.target
Wants=network-online.target

[Service]
Type=notify
ExecStart=/usr/bin/rclone mount gdrive: %h/gdrive \
  --config %h/.config/rclone/rclone.conf \
  --vfs-cache-mode full \
  --vfs-cache-max-size 10G \
  --vfs-cache-max-age 24h \
  --vfs-write-back 5s \
  --dir-cache-time 24h \
  --poll-interval 1m \
  --drive-chunk-size 64M \
  --umask 022 \
  --allow-other
ExecStop=/bin/fusermount -u %h/gdrive
Restart=on-failure
RestartSec=10

[Install]
WantedBy=default.target

VFS Flag Reference

  • --vfs-cache-mode full: Caches chunks of files on your local SSD (~/.cache/rclone/vfs/gdrive/), enabling seamless random reads/writes and memory-mapped files.
  • --vfs-cache-max-size 10G: Caps local cache storage at 10 GB with Least Recently Used (LRU) eviction.
  • --vfs-write-back 5s: Batches rapid successive writes before streaming them to the cloud.
  • --dir-cache-time 24h & --poll-interval 1m: Caches directory hierarchies in RAM and polls Google’s Changes API every 60 seconds to keep listings updated without expensive rescanning.
  • --allow-other: Permits non-root processes and Windows 9P shares to access the mount.

Understanding VFS Mechanics: Locks and Asynchronous IO

When integrating a cloud backend (like Google Drive) into a local POSIX-compliant filesystem via FUSE, two critical mechanics come into play: Read/Write Locks and Asynchronous Uploads.

Read/Write Locks

Native filesystems (like ext4 on Linux or NTFS on Windows) use strict file locking mechanisms to prevent data corruption. If Program A is writing to a file, the operating system places a “write lock” on that file so Program B cannot overwrite the data simultaneously.

Cloud storage APIs (like Google Drive, Dropbox, or S3) do not support POSIX file locking natively—they simply accept REST API HTTP uploads. When multiple remote clients edit the same file simultaneously, the last upload silently overwrites the previous ones, potentially causing data loss.

When using Rclone with FUSE, the local rclone mount daemon “fakes” POSIX locks for the local operating system. If two local applications try to write to ~/gdrive/document.txt simultaneously, Rclone respects the OS lock semantics and blocks the conflicting request at the local FUSE layer. However, this lock is strictly local to your machine. If you edit the file from your WSL mount while a collaborator edits the same file via the Google Drive web interface, the cloud server will not reject either write, and version conflicts may occur.

Asynchronous Uploads (--vfs-cache-mode writes or full)

Uploading data to the cloud is bottlenecked by your ISP upload speed and HTTP latency. Without a VFS cache, if a local application attempts to save a 50 MB video edit directly to the mounted network drive, the application UI would completely freeze (hang) until the entire HTTP POST upload finishes.

By setting --vfs-cache-mode full (or writes), Rclone completely detaches the local application’s file I/O operations from the network transfer: 1. The application writes the 50 MB file directly to your local SSD cache (~/.cache/rclone/vfs/gdrive/). 2. FUSE immediately reports back to the application: “Success! File written.” 3. The application resumes functioning instantly without any lag, freezing, or I/O bottleneck. 4. In the background, Rclone adds the file to a queue and asynchronously uploads it to Google Drive using the delay defined by --vfs-write-back 5s (waiting 5 seconds to see if the application makes further rapid changes before initiating the upload).

This architecture guarantees native NVMe SSD performance for local software while providing seamless, invisible cloud synchronization.

Step 6: Enable and Start the Service

Reload the user daemon, enable the service, and turn on session lingering:

systemctl --user daemon-reload
systemctl --user enable --now rclone-gdrive.service
sudo loginctl enable-linger $USER

Check the active status:

systemctl --user status rclone-gdrive.service

You should see an active status with Mounted gdrive: at /home/<user>/gdrive.

Step 7: Map the Mount as a Native Windows Drive

Once the drive is mounted inside WSL, it is directly exposed to Windows over the internal network share \\wsl$\.

  1. Open Windows File Explorer (Win + E).

  2. In the address bar, navigate to your WSL distribution’s mount path:

    \\wsl$\Ubuntu\home\<your-wsl-username>\gdrive

    (Replace Ubuntu with your distro name if running Debian, Arch, etc., and <your-wsl-username> with your actual Linux user).

  3. Right-click on the gdrive folder in the breadcrumb bar or navigation tree and select Map network drive…

  4. Select your preferred drive letter (e.g., G:).

  5. Check Reconnect at sign-in and click Finish.

Your Google Drive will now appear under This PC alongside C:\ as a fully functioning local drive.

Step 8: Ensuring Background Persistence

On standalone Linux, systemd runs continuously. On Windows, however, WSL2 enters a dormant state when no interactive shells or active processes are running.

To keep your Rclone mount and systemd timers running in the background whenever Windows boots:

  1. Press Win + R, type taskschd.msc, and press Enter.
  2. Click Create Basic Task:
    • Name: Start WSL Background Services
    • Trigger: When I log on (or When the computer starts)
    • Action: Start a program
    • Program/script: wsl.exe
    • Add arguments: -d Ubuntu -e sleep infinity
  3. Check Open the Properties dialog upon completion, and set the task to run hidden so no terminal window appears.

This single background process prevents the WSL VM from shutting down, ensuring systemd timers, file syncing, and network drive access remain uninterrupted.

Operational Runbook & Diagnostics

Operation Command
Check service health systemctl --user status rclone-gdrive.service
View real-time mount logs journalctl --user -u rclone-gdrive.service -f
Restart the mount daemon systemctl --user restart rclone-gdrive.service
Force graceful unmount fusermount -u ~/gdrive
Emergency lazy unmount fusermount -z -u ~/gdrive
Inspect local cache usage du -sh ~/.cache/rclone/vfs/gdrive/
Purge local VFS cache rm -rf ~/.cache/rclone/vfs/gdrive/*

With this setup, you retain all the power, automation, and speed of an Arch Linux Rclone configuration while benefiting from native Windows desktop integration!
