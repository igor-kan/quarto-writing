PHYD57H3: Advanced Computational Methods in Physics bridges the gap between theoretical physics and high-performance scientific computing. Successfully navigating the course requires more than just understanding mathematical models—it demands a solid grasp of the underlying infrastructure, from Linux distributions to compiler toolchains, SSH mechanics, and remote file manipulation.

This guide provides an end-to-end technical reference covering: 1. The curriculum tech stack and compiler toolchains. 2. An architectural comparison of Linux distributions (why Rocky Linux is preferred over Ubuntu/Arch for HPC). 3. The anatomy of the ssh command and all essential connection options. 4. An analysis of the filesystem artifacts on the university’s art-1 cluster. 5. Techniques for viewing and editing remote files locally (SSHFS, VS Code glibc workarounds, screen). 6. Bidirectional file transfers via SCP, Rsync, and graphical/CLI FTP and SFTP.

1. The Curriculum Tech Stack

To run physics simulations efficiently (such as Monte Carlo methods, Eulerian/Lagrangian fluid dynamics, and N-body gravitational solvers), the course relies on a specialized high-performance stack:

Programming Languages

  • C / C++: Used for low-level memory control and multi-dimensional array manipulation. You will learn to write high-performance C routines and call them directly from Python wrappers.
  • Fortran (F95 / 2008): Far from a dead language, modern Fortran remains unparalleled in contiguous numerical array operations and scientific computing. The course emphasizes modern syntax (lowercase, no legacy ALL CAPS).
  • Python 3: Utilized as a high-level scripting glue to steer simulations, parse output files, and generate interactive plots.

High-Performance Computing (HPC) & Parallelization

Modern scientific computing is impossible without parallel computing APIs: * OpenMP: Used for CPU shared-memory multithreading (fork-join parallelism) in both C and Fortran loops. * CUDA (C/C++ & Fortran): NVIDIA’s parallel computing platform for GPU acceleration, used to scale tasks like fluid dynamics, Poisson solvers, and Fourier transforms. * MPI (Message Passing Interface): The industry standard for distributed-memory parallelization across networked supercomputing cluster nodes.

Enterprise Compilers

You will work across several enterprise compiler toolchains: * gcc / g++ (GNU C/C++ Compiler) * gfortran (GNU Fortran Compiler) * ifort / ifx (Intel OneAPI Fortran Compiler) * nvcc / nvfortran (NVIDIA CUDA HPC Compilers)

CLI Environment & Graphics

  • Shells: bash and tcsh.
  • Terminal Editors: vim and nano.
  • Scientific Graphics: DISLIN, a high-level data plotting library linked into C and Fortran programs.

2. Comparing Linux Distributions: Why Rocky Linux?

The UTSC computing clusters span multiple generations: the legacy node art-1 runs on CentOS 6.6, while the modern node art-16 runs on Rocky Linux 9.6. If you plan to set up a local Virtual Machine, dual-boot, or WSL environment, here is how the relevant distributions compare:

The Red Hat Family (The HPC Supercomputing Standard)

These distributions share the same core architecture, .rpm binary package format, and dnf/yum package managers. * RHEL (Red Hat Enterprise Linux): The commercial standard for enterprise computing, government laboratories, and supercomputing clusters. Engineered for decade-long stability and binary reproducibility. * Rocky Linux: A 100% free, bug-for-bug downstream clone of RHEL. Following Red Hat’s deprecation of standard CentOS, Rocky Linux emerged to preserve enterprise-grade stability without licensing costs. This is why UTSC runs Rocky Linux 9.6 on art-16. * Fedora: The upstream rapid-release proving ground for Red Hat. It receives experimental features, cutting-edge kernels, and new GCC releases every 6 months. Excellent for desktop workstations, but too volatile for reproducible physics research.

Alternative Distributions

  • Ubuntu (Debian-based): The most popular general-purpose distro, using .deb packages and apt. While excellent for web servers and personal development, its package names, configuration hierarchies, and system libraries differ from the Red Hat ecosystem used on university clusters.
  • Arch Linux: An ultra-bleeding-edge rolling release distribution. It has no frozen release versions and receives daily package updates. While favored by power users, Arch is the opposite of an HPC cluster, where compiler and library versions must remain frozen to ensure numerical reproducibility across academic terms.

[!TIP] Recommended Local Environment For your laptop (via WSL2 or VirtualBox), install Rocky Linux 9. This guarantees 1:1 command, compiler, and package manager (dnf) parity with the university’s modern compute nodes.

3. The ssh Command & Connection Options Deep-Dive

Secure Shell (SSH) is the standard protocol for encrypted terminal access over untrusted networks. The fundamental syntax is:

ssh [options] [user@]hostname [command]

To connect to the UTSC cluster node art-1, you run:

ssh -X -o HostKeyAlgorithms=+ssh-dss phyd57@art-1.utsc.utoronto.ca

Dissecting the Command and Options

Option / Flag Purpose & Technical Mechanism
phyd57@art-1.utsc.utoronto.ca Specifies the remote user account (phyd57) and fully qualified domain name (FQDN) of the server.
-o HostKeyAlgorithms=+ssh-dss Mandatory for art-1. Tells the local OpenSSH client to accept legacy Digital Signature Algorithm (DSA) host keys.
-X Enables X11 Forwarding with security extensions (untrusted mode). Forwards graphical windows (e.g., DISLIN plots) back to your local display.
-Y Enables Trusted X11 Forwarding. Bypasses security restrictions; required if complex GUI programs crash under -X.
-p <port> Specifies the remote SSH port (default is 22). Example: ssh -p 22 user@host.
-C Enables gzip compression on all data streams (stdin, stdout, stderr, and X11). Dramatically improves responsiveness over slow Wi-Fi.
-i <identity_file> Passes a private key file for key-based authentication instead of typing a password. Example: ssh -i ~/.ssh/id_rsa user@host.
-t Forces pseudo-terminal allocation. Essential when launching interactive screen/tmux sessions or jumping between nodes.
-o ServerAliveInterval=60 Sends a keepalive null packet every 60 seconds to prevent network firewalls or NAT routers from dropping idle sessions.
-o ServerAliveCountMax=3 Drops connection only if 3 consecutive keepalive packets fail to return an acknowledgment.

Why Is -o HostKeyAlgorithms=+ssh-dss Required on art-1?

CentOS 6.6 runs an older OpenSSH server daemon (sshd) that advertises host identity using 1024-bit DSA keys (ssh-dss). Modern OpenSSH client releases (version 7.0 and later) deprecated and disabled ssh-dss out-of-the-box due to known cryptographic weaknesses in 1024-bit discrete logarithm implementations.

Without -o HostKeyAlgorithms=+ssh-dss, modern clients immediately abort the handshake with:

Unable to negotiate with 142.1.xxx.xxx port 22: no matching host key type found. Their offer: ssh-dss

The + sign instructs your local client to append ssh-dss to its allowed list of host key algorithms for this session.

Streamlining with ~/.ssh/config

Rather than typing long flags each time, configure a profile in ~/.ssh/config:

nano ~/.ssh/config

Add the following block:

Host art-1
    HostName art-1.utsc.utoronto.ca
    User phyd57
    HostKeyAlgorithms +ssh-dss
    ForwardX11 yes
    Compression yes
    ServerAliveInterval 60
    ServerAliveCountMax 3

Host art-16
    HostName art-16.utsc.utoronto.ca
    User phyd57
    ForwardX11 yes
    ServerAliveInterval 60

Set strict file permissions:

chmod 600 ~/.ssh/config

Now, connecting to either cluster is as simple as:

ssh art-1
# or
ssh art-16

5. Local Viewing & Editing of Remote Code

Developing directly over terminal SSH using basic Vim or Nano can slow down debugging. Here is how to view and edit files using modern local developer tools:

Method 1: SSHFS (Virtual Directory Mount) — Recommended

SSHFS mounts the remote cluster folder directly into your local filesystem over SFTP, allowing you to open remote files in local VS Code, Cursor, or Neovim with full language server protocol (LSP) support.

# 1. Create a local mount directory
mkdir -p ~/mounts/art-1

# 2. Mount using your ~/.ssh/config alias
sshfs art-1:/home/phyd57 ~/mounts/art-1 -o reconnect,ServerAliveInterval=15,ServerAliveCountMax=3

# 3. Open your personal folder in local VS Code
code ~/mounts/art-1/igor-dir

# 4. Unmount cleanly when finished
fusermount -u ~/mounts/art-1

(macOS users: install via brew install macfuse gromgit/fuse/sshfs-mac and unmount using umount ~/mounts/art-1).

Method 2: VS Code “SSH FS” (Bypassing CentOS 6 Glibc Limits)

The official VS Code Remote - SSH extension automatically deploys a remote Node.js server agent that requires glibc 2.28+. Because CentOS 6.6 ships with glibc 2.12, the extension crashes with:

/lib64/libc.so.6: version `GLIBC_2.28' not found

The Solution: Install the client-side SSH FS extension (HuFlungDu.ssh-fs or liximomo.sftp). This extension runs pure SFTP from your local machine, allowing file browsing and editing inside VS Code without requiring modern glibc libraries on the cluster.

Method 3: Terminal Persistence with screen

If you edit directly inside the remote shell, protect long-running compilations and simulations against network drops using screen:

# Start a detached-capable session
screen -S simulation_run

# Compile and execute
make && ./nbody

# Detach session: Press Ctrl+A, then D
# Reattach later:
screen -r simulation_run

6. Bidirectional File Transfers & FTP/SFTP

Moving files, datasets, and plots between your computer and art-1 can be done via CLI or graphical interfaces.

1. scp (Secure Copy Protocol)

  • Download a file to your local directory:

    scp art-1:~/finalD57-Q-2024.txt ./

  • Download your entire workspace recursively:

    scp -r art-1:~/igor-dir ./backup_igor_dir/

  • Upload source code to your cluster folder:

    scp ./my_solver.c art-1:~/igor-dir/

2. rsync (Differential Fast Synchronization)

rsync only transfers binary delta changes, making it far superior to scp for recurring project backups:

# Pull remote updates to local folder
rsync -avzP art-1:~/igor-dir/ ./local_igor_dir/

# Push local edits to cluster
rsync -avzP ./local_igor_dir/ art-1:~/igor-dir/

3. FTP & SFTP (GUI & CLI)

Because art-1 blocks unencrypted FTP (port 21), all FTP transfers must use SFTP (SSH File Transfer Protocol) over port 22.

Graphical FTP Clients (FileZilla, WinSCP, Cyberduck)

  1. Protocol: Select SFTP - SSH File Transfer Protocol (Do not choose FTP).
  2. Host: art-1.utsc.utoronto.ca
  3. Port: 22
  4. User: phyd57
  5. Password: [Password provided in lecture / saved in course private draft]

[!NOTE] GUI Client Legacy Host Key Note: Because of CentOS 6.6’s legacy DSA host keys, strictly updated FTP clients (such as latest FileZilla) may drop the connection. If this occurs, enable legacy host keys under FileZilla’s SFTP settings, or use WinSCP (Windows) or Cyberduck (macOS/Windows), which negotiate legacy ciphers automatically.

Interactive Command-Line sftp

sftp art-1
  • ls / lls : List remote / local directory contents.
  • cd <dir> / lcd <dir> : Change remote / local directory.
  • get <remote-file> : Download file.
  • put <local-file> : Upload file.
  • exit : Quit session.

7. Automated Local Backup Script

To safeguard your work inside igor-dir/, save this script locally as sync_art1.sh:

#!/usr/bin/env bash
set -euo pipefail

REMOTE_HOST="art-1"
REMOTE_PATH="~/igor-dir/"
LOCAL_BACKUP_DIR="${HOME}/backups/phyd57/$(date +%Y-%m-%d)"

mkdir -p "${LOCAL_BACKUP_DIR}"

echo "Syncing ${REMOTE_HOST}:${REMOTE_PATH} to ${LOCAL_BACKUP_DIR}..."
rsync -avzP \
  --exclude="*.x" \
  --exclude="*.o" \
  "${REMOTE_HOST}:${REMOTE_PATH}" "${LOCAL_BACKUP_DIR}/"

echo "Backup complete at $(date)."

Run with:

chmod +x sync_art1.sh
./sync_art1.sh
